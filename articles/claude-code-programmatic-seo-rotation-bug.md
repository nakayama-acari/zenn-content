## 実行する前に、答えが分かってしまった

このAI営業会社は副業SEOサイト（Next.js・Vercelホスティング）に、AIツールのレビュー記事を週1本のペースで自動生成・追加している。担当は `scripts/generate-content.mjs` という1本のNode.jsスクリプトで、深夜スケジューラから週次で起動される。

ある週、いつも通りこのスクリプトを実行する前に、次に選ばれるツールを手計算してみた。すると、**実行する前から「今週もWriteesonicが選ばれる」という答えが出てしまった。** 前回（1週間前）の実行でも同じツールが選ばれていたからだ。バグはまだ1文字も直っていないのに、結果だけ先に分かってしまった状態だった。

## 原因はたった1行の選定ロジック

犯人は次の1行だった。

```js
const todaysTool = aiTools[new Date().getDate() % aiTools.length];
```

`aiTools` は当時3件だけの配列（Jasper AI / Writesonic / Claude API）。`new Date().getDate()` は「今日が何日か」（1〜31）を返すので、これを配列の長さ3で割った余りでツールを選ぶ、という設計だった。ロジック単体を見れば破綻はしていない。問題は、この関数が**週1回しか呼ばれない**という運用条件と組み合わさったときに起きた。

## 3日周期の関数を、7日周期でしか呼ばない

`% 3` は3日で一周する。だがこの関数は7日に1回しか実行されない。3と7は互いに素なので、本来は21日（3と7の最小公倍数）かけて全パターンを巡回するはずだった。ところが実際に起きたのは、もっと単純な一致だった。

実行日を実際の日付で検算するとこうなる。

| 実行日 | `getDate() % 3` | 選ばれるツール |
|---|---|---|
| 7/28 | `28 % 3 = 1` | Writesonic |
| 8/4 | `4 % 3 = 1` | Writesonic |

7月28日の実行から次の実行（8月4日）までは、暦の上ではちょうど7日進んでいる。だが `% 3` の世界では `28 % 3` と `4 % 3` がどちらも1になり、**同じ余りに着地してしまった**。これは偶然ではなく、7日ごとに実行するかぎり毎回起こりうる構造的な問題だった。日付が7ずつ増えるとき、`% 3` の結果は `+7 % 3 = +1` ずつしかズレない。つまり3回に1回（21日に1回）しか余りが変わらず、「週1実行」という運用のリズムと「日付を3で割る」という選定ロジックのリズムが噛み合っていなかった。

外から見える症状は「同じツールが2週間おきに再登場する」という地味なものだったので、記事の本数は着実に増えていたし、Vercelのデプロイも毎回成功していた。何もエラーが出ていないぶん、実行するまで気づけない類のバグだった。

## 直したのは「周期を変える」ではなく「周期に頼らない」

`% 5` や `% 7` に変えれば当座はズレるが、対象ツールを増やすたびにまた同じ罠を踏みかねない。そこで採用したのは、日付演算そのものをやめて、**「すでに書いた記事」を毎回スキャンして、まだ書いていないツールを優先的に選ぶ**という方式だった。

```js
// 既存記事ファイル名（-review.md）に含まれるツール名スラッグを収集し、
// まだレビューが存在しないツールを優先的に選ぶ。全ツール網羅済みなら従来通り日付ローテーションにフォールバック。
const articlesDir = path.join(process.cwd(), OUTPUT_DIR);
const existingFiles = fs.existsSync(articlesDir) ? fs.readdirSync(articlesDir) : [];
const slugify = (name) => name.toLowerCase().replace(/\s/g, "-");
const coveredSlugs = new Set(
  existingFiles
    .filter((f) => f.endsWith("-review.md") || f.includes("-affiliate-"))
    .map((f) => f.replace(/^\d{8}-/, "").replace(/-review\.md$/, "").replace(/^affiliate-/, "").replace(/\.md$/, ""))
);
const uncoveredTools = aiTools.filter((t) => !coveredSlugs.has(slugify(t.name)));
const todaysTool = uncoveredTools.length > 0 ? uncoveredTools[0] : aiTools[new Date().getDate() % aiTools.length];
```

ポイントは2つ。1つは、状態（次に何を選ぶべきか）を日付という外部の周期変数から計算するのをやめて、**実際に生成済みのファイル一覧という一次情報**から毎回導き出すようにしたこと。もう1つは、候補プールを3件から8件に増やして、そもそも周期がすぐ一巡しないようにしたこと。全ツールを一通り紹介し終えたときだけ、従来の日付ローテーションにフォールバックする設計にして、無限に候補が尽きる心配もなくした。

## この教訓の汎用パターン

「日付や実行回数を法（mod）で割って何かを選ぶ」というローテーション設計は、プログラマティックSEOに限らずよく使う。だが、**選定ロジックの周期と、それを呼び出す運用の周期が独立変数である**ことを忘れると、この記事のような「たまたま一致して固定化する」事故が起きる。3や7のような小さい数同士の組み合わせは特に、割り切れる／割り切れないの境目が直感で読みにくい。

再発防止として持ち帰れる工程は次の2つだ。

- **周期性のあるロジックを新しく組んだら、実行前に実際の日付を数値で代入して検算する。** 「たぶん大丈夫」を1回の掛け算・剰余計算に落とすだけで、今回のような一致は事前に見つけられる。
- **可能なら「次に何をすべきか」を外部の周期変数（日付・実行回数）ではなく、実際の生成物・状態から都度算出する設計に寄せる。** 日付ベースのローテーションは実装が楽な分、運用の実行周期とズレたときに気づきにくい沈黙のバグになりやすい。

自動化スクリプトの「動いているように見える」は、今回のように中身が固定化していても成立してしまう。記事の本数が順調に増えているという結果だけでなく、**その中身が実際に多様化しているか**まで、たまに検算する価値がある。
