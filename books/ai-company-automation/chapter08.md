## この章で学ぶこと

- 「教訓をMDファイルに書く」だけでは再発防止にならないという、実際に起きた事例
- 1つの部署の失敗が、全社共有ファイルへ"昇格"する（あるいはしない）仕組み
- 「30日以上再発していない」と認定できた項目が、実はまだ0件だという現実

## 実際のシステム構成

このシステムには、各エージェントの失敗を記録する `output/<部署名>/lessons_learned.md` と、全19エージェントが毎回のセッション開始時に読み込む `memory/company_lessons.md`（CEOが週次で集約）の2層がある。fukugyo自身の教訓ファイルは、以下の5カテゴリで構成されている。

```
❌ NGパターン（してはいけないこと）
✅ GOODパターン（うまくいったこと）
⚠️ 注意事項（気をつけること）
📈 成功した戦略・アプローチ
🏆 吸収済み（30日以上再発なし）
```

このうち「🏆 吸収済み」の欄は、この章を書いている時点でも空欄のままだ。コメントアウトされたテンプレート行が1つ残っているだけで、実際のエントリはまだ1件も入っていない。教訓ファイル自体は6月末の作成以来ずっと運用されているのに、「もう二度と起きない」と言い切れた項目が、これまでにひとつも無いということになる。

### 3日連続で再発した、同じ不具合の記録

一番わかりやすい実例は、X投稿の送信確認処理だ。`fukugyo_x_post.js` は投稿ボタンを押した後、Xの内部レスポンス（CreateTweet）が返ってくるかどうかを見て成功判定する。このタイミングがずれると `X_POST_NOT_CONFIRMED` というエラーになる。

記録を日付順に並べると、こうなっている。

```
07-03: 2回連続失敗 → 確認スクリプトで未投稿と判定 → 3回目で成功
07-04: 前日と全く同じ挙動が再現（2回失敗→3回目成功）
07-10: 7回連続失敗という、これまでで最悪のケース
07-12: 5回連続失敗が再発
07-13: 3日連続で「高頻度の失敗」というパターン自体が固定化
```

07-04時点の教訓ファイルには、すでにこう書かれていた。「単発の偶発事象ではなく高頻度の再現性がある不具合と見てよい」。それでも07-10には7回連続という、それまでで最悪の失敗が起きている。教訓を書いた3日後に、書いた本人（正確には同じ役割の別セッション）が、より悪化した形で同じ壁にぶつかっていた。

## なぜこの設計にしたか

**失敗した前提：「書けば次は気をつけるはず」**

最初の設計は素朴だった。失敗したらMDファイルに書く。次のセッションはそれを読む。読めば同じミスは避けられるはず——という前提だった。

だが `memory/company_lessons.md` には、この前提そのものを否定する記録が残っている。

> memory/preferencesはあくまで次回セッションの"心構え"であり、harnessが強制執行するhooksとは強制力が違う。将来のセッションが指示を忘れる・別部署が同じ操作をする等のリスクがある運用ルールは、hook化した方が確実

MDファイルは「読んでから行動する」ことを前提にした仕組みで、読み飛ばしたり、読んでも状況判断を誤ったりする余地がそのまま残る。実際、X投稿の不具合は文章で3回警告されたあとも解消せず、最終的に効いたのは「2〜3回で成功しなければ5回前後で打ち切り、次回セッションに持ち越す」という運用ルールを07-10に追加したことだった。原因そのもの（Playwrightのクリック処理）を直す代わりに、失敗の被害を最小化する運用でまず止血した、という形になる。

**採用した設計：気づいたその場で聞く**

CLAUDE.mdには「リアルタイム教訓検知」という手順がある。オーナーが「違う」「ダメ」「やり直し」といった言葉を発した瞬間に作業を止め、「これを教訓として記録しますか？」と確認してから `/remember` で保存する。書き溜めてから振り返るのではなく、指摘が出た瞬間に記録する設計にしてあるのは、時間が経つほど「何が具体的にダメだったか」の解像度が落ちるからだ。

## 実装のポイント

### 部署をまたぐ教訓は、自動では伝わらない

2026-07-07、fukugyoはGoogle Drive MCPの `create_file` が無言で失敗する原因を突き止めた。正しい引数名は `title` / `textContent` / `contentMimeType` / `parentId` で、GAS/GCPで一般的な `name` / `content` / `mimeType` / `parents` ではない。この時点でfukugyoの教訓ファイルには、こう書き残されている。

> この教訓はcompany_lessons.md（CEO管理の全社共有ファイル）には未記載のため、他部署でも同じ理由で無言失敗している可能性が高い。trainerまたはCEOに共有し、company_lessons.mdへの反映を提案すること。

この章を書いている時点で `company_lessons.md` を検索しても、この引数名の教訓は見つからない。提案したこと自体は記録に残っているが、実際に全社ファイルへ昇格したかどうかは確認できていない。1部署の教訓は、誰かが明示的に「これは他部署にも関係する」と判断して橋渡ししない限り、自動では横に広がらない。

### 診断の順序を間違えると、正しいデータでも誤読する

07-13、note有料記事の購入が3週連続0件になった。「ピボット基準」に達した数字だったが、教訓ファイルにはこう続く。

> 露出（PV）が転換率を評価できる母数（目安20PV以上）に達していない状態で価格だけ動かしても、何が効いたか分からなくなる。先に露出を増やしてから、それでも0件なら価格を動かす。

購入0件という同じ事実に対して、「価格が高い」と「そもそも読まれていない」の2つの仮説が立つ。ここで先に価格を動かしていたら、その後もし購入が増えても減っても、何が効いたのか永久にわからなくなっていた。数字が同じでも、診断の順序を間違えると対応そのものを誤る、という記録として残している。

## この章のまとめ

| 気づき | 実際どうしたか |
|---|---|
| 教訓を書いても翌日また同じミスをする | 運用ルール化（打ち切り基準など）で被害を止血し、原因修正は別途依頼する |
| 部署間で教訓は自動共有されない | 「これは他部署にも関係する」と気づいた側が明示的に橋渡しを提案する（成功したとは限らない） |
| 同じ数字でも診断の順序で結論が変わる | 母数が足りないうちは価格などの変数を動かさず、先に露出を増やす |
| 「30日再発なし」に到達した項目 | この章を書いている時点で0件 |

この本の第1章から第7章まで、毎回「実際に動いている」と書いてきたが、それは「一度も壊れなかった」という意味ではない。壊れて、直して、また似た形で壊れて、また直す——その繰り返しの記録そのものが、このシステムの実態に一番近い。
