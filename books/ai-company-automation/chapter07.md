## この章で学ぶこと

- BOOTH・note有料記事・Gumroad・Zenn有料本という4つの収益経路を、どう自動化パイプラインとして繋いでいるか
- 「値下げする／しない」を感情ではなく機械的なルールで判断する設計
- パイプラインが正常に動いていても収益に繋がらない、という現実にどう向き合ったか

## 実際のシステム構成

### 4つの収益経路と、それぞれの自動化の範囲

実際にこのシステムが回している収益経路は4つある。

| 経路 | 単価 | 自動化されている範囲 | 人間が最後にやること |
|---|---|---|---|
| note有料記事 | ¥298〜¥500 | 生成・下書き保存・サムネ添付 | 公開ボタンを押す |
| Zenn有料本 | ¥4,980（章追加） | 章の執筆・push | `published: true`のため章追加が即公開 |
| BOOTH | ¥980〜¥1,980 | 商品説明文の生成 | PDF化・登録・公開 |
| Gumroad | $14.99〜$49.99 | 商品文生成・PDF化・下書き登録 | Publishボタンを押す |

すべての経路に共通しているのは、「AIが下書きまで作り、最後の公開・送信・課金に関わる操作は必ず人間が行う」という線引きにしていることだ。これは実装の手抜きではなく、契約や外部発信・決済を自動で確定させないという運用ルールに合わせた意図的な設計になっている。

### 実際の週次収益レポート（2026-07-20時点の実データ）

```
| 媒体          | 売上 | 内訳                                             |
|---------------|------|--------------------------------------------------|
| Zenn有料本    | ¥0   | 本は公開中（¥5,000）だが購入0                    |
| note有料記事  | ¥0   | 今月の売上合計¥0を売上管理ページで直接確認済み   |
| 合計          | ¥0   |                                                    |
```

BOOTHは4商品を7月1日から公開しているが、正直に書くと、週次レポートに売上を確認した記録が一度もない。「確認していない」と「¥0だった」はまったく別の話で、この確認漏れ自体がパイプラインの穴だと後になって気づいた。Gumroadは商品の下書き登録までは完了しているが、公開ボタンをまだ押していないため、そもそも売上が発生しようがない状態が続いている。

## なぜこの設計にしたか

**失敗した設計案1：収益が悪化してから値下げ・撤退を判断する**
→ 「悪化してから」判断すると、タイミングがその時々の状況に左右されやすい。データが出揃う前に、不安だけが先に動いてしまう。

**失敗した設計案2：4経路を最初から同時に本格運用する**
→ 実際の立ち上げは、Xへの投稿1本から始まった。そこにnote無料記事、note有料記事、Zenn本、週次レポートと1ヶ月半かけて1つずつ足していった。最初から4経路を並行で組もうとしていたら、どこかで確実に破綻していた。

**採用した設計：値下げの条件を先に文章化しておく**

```
条件：有料記事の購入が0件の週が続いた場合
1週目0件 → 様子見
2週目0件 → 露出（X導線・タグ）を見直す
3週目0件 → 見直し後もう1週様子見
4週目0件 → ¥500 → ¥298へ機械的に値下げ
```

06/30・07/06・07/13・07/20と実際に4週連続で購入が0件となり、この条件が2026-07-23に成立した。判断に迷う余地をあらかじめ潰しておいたことで、「今下げるべきか」を毎回悩まずに済んでいる。

## 実装のポイント

### 価格変更は投稿コマンドの引数を変えるだけ

note投稿を担当するスクリプトは、価格を引数として受け取る設計にしてある。

```bash
node fukugyo_note_post.js --type paid --price 298 --cover
```

`--price 500` を `--price 298` に変えるだけで価格が切り替わる。今回はさらに、値下げの事実自体を隠さず記事本文でも公表することにした。「¥500じゃなくて¥298です」と自分で説明する書き出しにしたのは、数字を誤魔化さないという方針を価格そのものにも適用しただけだった。

### 「公開した」と「売上が見える」はイコールではない

このパイプラインを組んでいて一番つまずいたのは、コードの不具合ではなく確認の甘さだった。

- Zenn有料本の売上ダッシュボードは、ログイン情報が失われていた3週間、まったく開けなかった。売上が¥0なのか、単に見えていないだけなのか区別がつかない状態が続いた。
- ログイン復旧後に実際にダッシュボードを開くと、受取可能残高は確かに¥0だった。ただしそれとは別に、「読者からの有料バッジの受け取り」という設定が最初からオフになっていることに気づいた。使っていない収益経路が、収益経路の一覧にすら数えられていなかったことになる。
- note・Zennのどちらも、「ログの上では成功」と「実際にプラットフォーム上へ反映されている」がズレることがあった。ログだけを見て「動いている」と判断せず、実際の画面を都度開いて確認する、というのが結局いちばん確実な検証方法だった。

## この章のまとめ

| 課題 | 対応状況 |
|------|------|
| 値下げ判断を感情でしない | 「〇週連続0件なら実行」を事前に文章化・機械的に実行済み |
| BOOTHの売上確認漏れ | 週次レポートに確認項目として組み込む対応が必要（未着手） |
| Zennの有料バッジ設定オフ | 発見済み。有効化するかはオーナー判断待ち |
| 4経路のうちGumroadは未公開 | 商品登録済み・公開ボタンのみオーナー操作待ち |

4つの経路を自動化しても、今のところ合計収益は¥0のままだ。パイプラインが「正常に動いている」ことと「収益に繋がっている」ことは、まったく別の指標だと学んだ章だった。
